# Gap closure (A9 follow-up) — decisions

Format: `[YYYY-MM-DD] [Topic]: Decision -> Reason (why alternatives failed)`

- [2026-10-22] [my_groups]: added `public.my_groups()` (private + INVOKER) returning the caller's ACTIVE groups in one call -> the "Meus Grupos" screen needed FOUR round trips (group_members -> groups -> member count -> group_featured); the RPC reuses A3's own rules (member_count = the `group_members` count, `is_featured` = the `group_featured` flag) and A3's ACTIVE-membership rule (not archived; a challenge whose `ends_on` is in the past is excluded), so there is exactly ONE definition of "active" in the project.
- [2026-10-22] [my_groups / invite_code]: the invite code is returned ONLY to the group admin (`case when role = 'admin' then invite_code else null end`) -> the code is a CAPABILITY (SCHEMA.md §14.3); a member must not be able to read it out of a list endpoint. The rule is inside the SQL, not in the client, so a direct PostgREST call cannot leak it either.
- [2026-10-22] [my_groups / blocked caller]: a group whose CREATOR blocks the caller is excluded, using `private.is_blocked_impl(v_uid, g.created_by)` -> A4 already refuses a check-in into such a group with `blocked_by_group_creator`; mirroring it keeps the "Meus Grupos" list consistent with what the member can actually post in. The project's block relation is SYMMETRIC, so the same helper covers both directions.
- [2026-10-22] [feed_post_comments]: created `public.feed_post_comments` (the "encouraging comments" of the product plan were a SILENT NO-OP because no table existed) -> the comment is public group content; it is read by the members of the post's group, hidden from a blocked pair and moderated by the group admins.
- [2026-10-22] [feed_post_comments / no updated_at]: the table has NO `updated_at` column and NO `public.attach_updated_at` trigger -> a comment is effectively append-only; this mirrors `public.moderation_actions` (A6's audit trail) and avoids a second timestamp that no reader would trust.
- [2026-10-22] [feed_post_comments / column privileges]: `authenticated` gets `UPDATE (body)` ONLY (plus SELECT, INSERT on four columns, DELETE) -> the moderation columns (`is_hidden`, `hidden_reason`, `hidden_at`) stay SERVER-owned: a client cannot un-hide its own comment. A6 does the same for `prayer_intentions.prayer_count`.
- [2026-10-22] [feed_post_comments / privacy]: the table carries a `comment on table` that states a comment is public group content and must never hold a Spiritual Diary text, a Confession record or a private check-in reflection -> CONVENTIONS §8 makes the privacy invariant a hard build gate, and the upstream CHECKs (`feed_posts_no_confession`, `check_ins_private_has_no_content_ck`) guarantee that the content never reaches the feed in the first place.
- [2026-10-22] [feed comments / cursor]: `get_feed_post_comments` reuses A5's cursor EXACTLY (`"<created_at ISO-8601 UTC>|<row uuid>"`, `created_at DESC, id DESC`, `p_before` is `text`, `p_limit` clamped to 1..50) -> a second cursor format would mean a second pagination implementation and a second class of "skipped row" bugs; the composite cursor is the only strictly correct form when two rows share a `created_at`.
- [2026-10-22] [feed comments / visibility]: the RPCs resolve the post through A5's `private.a5_visible_post_group(post_id, uid)` -> it already encodes "member of the post's group AND not blocked with the author AND the post is not hidden (unless admin)"; reusing it means a comment can never be attached to a post the caller may not see, and it is the same visibility the feed itself uses.
- [2026-10-22] [feed comments / audit]: `soft_delete_feed_post_comment` writes ONE `audit_log` row with `action = 'feed.comment_removed'` and `target_type = 'feed_post_comment'` -> it mirrors A5's `soft_delete_feed_post` (`feed.post_removed` / `feed_post`) and A6's `chat.message_removed`, so the audit trail has ONE naming convention (`<domain>.<verb>`).
- [2026-10-22] [batch signed URLs]: `public.create_signed_witness_urls` calls A6's EXISTING `private.create_signed_witness_url_impl` once per path instead of re-implementing the path regex -> the batch is then guaranteed to apply the EXACT same checks (path shape, group membership, block) as the single-URL RPC, and there is only ONE copy of the regex in the database. A path that fails is caught, reported with `signed_url = null` + a `reason`, and never aborts the batch; the reason describes the CALLER's authorisation, so it never reveals whether the object exists.
- [2026-10-22] [batch signed URLs / how it signs]: the RPC does NOT sign on this deployment (there is no `storage.create_signed_url` helper — SCHEMA.md §18.3); it is the AUTHORISATION GATE and returns `signed_url = null` with `source = 'edge_function'` -> the `signed-witness-url` Edge Function signs it. Duplicating A6's `to_regprocedure('storage.create_signed_url(text,integer)')` probe would have been a second, divergent copy of the same decision.
- [2026-10-22] [batch signed URLs / Edge Function]: the `signed-witness-url` Edge Function now ALSO accepts `{ "object_paths": [...] }` and answers `{ items: [...] }` (the singular form is unchanged) -> without it the batch RPC alone would still cost N Edge Function calls, so the gap (a feed with N witness photos) would NOT be closed. The function calls the new batch RPC with the CALLER's JWT, so the authorisation stays per-user.
- [2026-10-22] [batch signed URLs / clamps]: `p_expires_in` is clamped to 60..3600 s and the array to 50 paths (`truncated: true` when there were more) -> the same TTL clamp as A6's single RPC, plus a bound on the request size so one call cannot be used to probe thousands of paths.
- [2026-10-22] [rls_matrix]: `supabase/tests/a10/rls_matrix.sql` was EXTENDED (not weakened) with the new table -> the file asserts that its expectation table covers EXACTLY the public tables and that the INSERT/UPDATE/DELETE policy sets are EXACTLY the documented ones, so a new public table necessarily breaks it; the only ways forward were to weaken the assertions (unacceptable) or to add the new table to the matrix (correct: the matrix's own contract is "for EVERY table of the public schema"). The plan went 647 -> 667 (+15 matrix cells, +5 INSERT probes); no assertion was removed, skipped or relaxed.
- [2026-10-22] [unindexed_foreign_keys]: added `idx_feed_post_comments_user_id` on `(user_id)` in a separate migration (1004) -> the advisor reported the new `user_id` FK as unindexed and the project keeps that lint at ZERO (A8 fixed the same lint in 0706); a separate migration avoids editing an applied migration file.
- [2026-10-22] [comment body length]: the 500-character limit is enforced TWICE — in `create_feed_post_comment` (22023) and by a CHECK constraint on the table -> the RPC gives the client a readable error, the CHECK makes the invariant un-bypassable by a direct PostgREST INSERT.
