# A6 — Storage, Moderation & Safety decisions

Format: `[YYYY-MM-DD] [Topic]: Decision -> Reason (why alternatives failed)`

- [2026-10-22] [Buckets]: created the buckets with `insert into storage.buckets` instead of the Storage API -> there is no Supabase MCP storage tool and no service-role key available to the agent; the SQL path is verified working (the `protect_bucket_control_columns` trigger only guards the lifecycle columns).
- [2026-10-22] [witness-photos]: `witness-photos` is PRIVATE and gets NO `anon` policy (not even a read) -> it holds prayer-witness photographs; the sacred-privacy gate (CONVENTIONS §8) requires that a witness photo is only ever visible to the members of the group it was shared in, and `anon` is unauthenticated.
- [2026-10-22] [witness path convention]: the path is `<group_id>/<user_id>/<uuid>.<ext>` INSIDE the bucket (`storage.objects.name` does not repeat the bucket id) -> `storage.foldername(name)` returns every segment except the file name, so `foldername[1]` is the group and `foldername[2]` is the uploader; the policy can therefore enforce "uploader = caller" and "caller is a group member" with two index lookups.
- [2026-10-22] [private.try_uuid]: every storage policy casts a path segment with `private.try_uuid(text)` instead of `::uuid` -> a malformed path segment would raise `22P02` inside the policy and turn a rejected upload into a 500; `try_uuid` returns NULL and the policy simply evaluates to false.
- [2026-10-22] [Signed URL]: the signed URL is created by the `signed-witness-url` Edge Function, not by SQL -> this deployment has NO `storage.create_signed_url` helper (verified against `pg_proc`: the `storage` schema exposes only `foldername`, `search`, `filename`, …). The SQL RPC stays the authorisation gate and returns the validated `object_path` + clamped TTL; the function signs with the service role.
- [2026-10-22] [Signed URL TTL]: the TTL is clamped to 60..3600 seconds inside the RPC -> a signed URL is a bearer token for a private photo; an unbounded or 1-second TTL is either unusable or a standing leak.
- [2026-10-22] [Report idempotency]: `report_content` returns the existing report when the SAME member reports the SAME target again instead of inserting a second row -> CONVENTIONS §3 requires mutating RPCs to be idempotent where the client may retry, and a single member must not be able to trip the auto-hide threshold alone.
- [2026-10-22] [Auto-hide threshold]: the threshold is 3 independent reports (`private.auto_hide_threshold()`), enforced by an `AFTER INSERT` trigger on `content_reports` -> one report is never enough, two is not enough, and the trigger fires for ANY insert path (not only the RPC), so a future admin tool cannot bypass it.
- [2026-10-22] [Auto-hide hiding]: the trigger hides the target through explicit, hardcoded `UPDATE` statements per `target_type` (never dynamic SQL on a caller-supplied table name) -> the target type comes from the caller; only the table name and the column list are literals in the code.
- [2026-10-22] [admin_delete_post]: the RPC DELEGATES to A5's `public.soft_delete_feed_post(p_post_id uuid)` instead of re-implementing the hide -> A5 owns the feed semantics (`hidden_reason = 'admin_removed'`) and the audit row; a duplicate implementation would drift. A6 only adds the `moderation_actions` + `audit_log` trail. A fallback (hide in place) exists in case A5's function is ever removed.
- [2026-10-22] [moderation_actions.action_type]: the CHECK constraint was extended with `action_report` -> the spec lists ten action types but a report a moderator *acteded* on has no matching type, so the resolution could not be recorded in the trail.
- [2026-10-22] [moderation_actions RLS]: no INSERT policy for `authenticated` on `moderation_actions` -> the rows are written only by the `security definer` RPCs; a client-writable trail could be forged.
- [2026-10-22] [content_reports.resolved_by]: `resolved_by` is deliberately NOT a foreign key -> same reasoning as `audit_log.actor_id`: the moderation history must survive the hard deletion of the moderator (A2's account erasure).
- [2026-10-22] [v_target_report_counts]: the view is `security_invoker = true` -> the counter must not leak the existence of reports about content the reader may not see; the underlying `content_reports` RLS then applies to the reader.
- [2026-10-22] [Private check-ins]: `report_content` refuses a check-in whose `sharing = 'private'` -> a private check-in carries no content (`reflection_text` and `photo_path` are NULL) and is never shared, so it must not even be referenceable by a moderation report (sacred-privacy gate, CONVENTIONS §8).
- [2026-10-22] [anon privileges]: every A6 function is revoked from `anon` EXPLICITLY, not only from `public` -> the project carries a default privilege that grants EXECUTE on new `public` functions to `anon`; `revoke … from public` leaves that explicit grant in place and PostgREST would expose the RPC unauthenticated (this was the `anon_security_definer_function_executable` finding, now fixed — migration 0505).
- [2026-10-22] [private schema]: the helpers live in the non-exposed `private` schema, mirroring A2/A3/A4/A5's `*_impl` pattern -> `private` is not in the PostgREST exposed schemas, so a `security definer` helper there cannot be called over HTTP.
- [2026-10-22] [chat moderation]: `hide_content('chat_message', …)` records the action but cannot hide the message -> `public.chat_messages` (A5) has no `is_hidden` column and A6 may not ALTER another agent's table; the request to A5 is recorded in the final report.
- [2026-10-22] [check_in hiding]: a reported check-in is hidden through the `feed_posts` rows that carry it (`check_in_id`), not through `check_ins` -> `check_ins` has no visibility flag (and its private rows must stay untouched); hiding the shared timeline entries is the only correct behaviour.
- [2026-10-22] [Edge Function auth]: the `signed-witness-url` function sends the project anon key in the `apikey` header and the CALLER's JWT in the `Authorization` header -> PostgREST rejects a user JWT used as an API key ("Invalid API key", 401); only the signing step may use the service role, so that `auth.uid()` stays the real user.
- [2026-10-22] [Edge Function parsing]: the bearer token is parsed with `split(' ')` instead of a regular expression -> the agent harness that deploys the function rewrites backslash escapes unpredictably (`\s` did not survive), and the split needs no escaping at all.
- [2026-10-22] [config.toml]: the local bucket declarations now match the production buckets (`avatars` public, `group-covers` public, `witness-photos` private) and the unused `check-in-proofs` bucket was removed -> A1's config declared `avatars`/`group-covers` as private and a `check-in-proofs` bucket that does not exist in the deployed project; the local stack must behave like production.
- [2026-10-22] [Migrations]: the A6 work was applied in several `apply_migration` calls under the names `create_storage_buckets`, `create_signed_witness_url`, `create_moderation_tables`, `create_moderation_rpcs` (twice), `create_moderation_public_rpcs` and `harden_a6_rpc_privileges` -> the migration tool derives a version from the name and refuses a duplicate version; the FILES `0501`–`0505` are the canonical source and replaying them from scratch produces the same schema.
- [2026-10-22] [Tests]: the pgTAP suite asserts the bucket flags, the policy inventory, the explicit absence of an `anon` policy on `witness-photos`, the block/unblock idempotency, the symmetric `is_blocked`, the 3-report auto-hide, the admin-only delete and the `content_reports` RLS -> 81 assertions, `verdict = PASS`; the file is wrapped in `begin; … rollback;` so nothing is persisted.
