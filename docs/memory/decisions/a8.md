# A8 — decisions — Guardian Angel & push notifications

## 2026-10-22 · Schema & privacy

- [2026-10-22] [Tables]: A8 owns `guardian_angel_opt_ins`, `guardian_angel_pairings`, `guardian_nudges`, `device_tokens`, `notification_outbox` (public) and `app_settings` (private) in the `0700` prefix range -> vertical slicing: the Guardian Angel mechanic and the push delivery plumbing live in one domain, and the outbox is the only seam to the Edge Function.
- [2026-10-22] [Sacred privacy]: none of the A8 tables can hold a Confession, a Spiritual Diary text or the content of a private check-in -> `guardian_angel_pairings` and `guardian_nudges` hold uuids and dates only, and the guardian sees a **display name** plus the group prayer intentions (public Prayer Wall content) — never the reflection or the photo of a check-in.
- [2026-10-22] [Guardian identity]: `public.guardian_angel_pairings` has **no client SELECT policy** and the table privilege is revoked for `anon`/`authenticated`; every read goes through the redacting RPCs -> RLS is row level, so a policy alone would still expose the `guardian_id` column to the protected member; revoking the privilege *and* redacting in the RPC is the only way to keep the identity secret until the cycle ends.
- [2026-10-22] [Nudge anonymity]: the client grant on `public.guardian_nudges` omits `sender_id` and the RLS policy only exposes the sender's own rows; the pushed body is *"Alguém rezou por você hoje."* and the payload carries only `{group_id, cycle_key}` -> the recipient must not be able to learn who prayed for them, neither from the row nor from the push.
- [2026-10-22] [Liturgical reminders]: the `notification_type` CHECK of `public.notification_outbox` accepts no liturgical value, and A8 created no liturgical trigger -> the Angelus, the Morning Offering and every other liturgical prompt are scheduled **on the device**; they are a personal rhythm, not a social event, and a sacred screen must never be interrupted by a server.
- [2026-10-22] [Blocked pairs]: every emission trigger checks `public.is_blocked(recipient, sender)` -> a block must silence the notifications in both directions, otherwise "block" would leave a channel open.

## 2026-10-22 · The draw

- [2026-10-22] [Derangement]: the draw is a **deterministic rotation by 1** over the eligible members sorted by `user_id` -> a rotation by 1 over `n >= 2` sorted elements is a true derangement (nobody keeps its own position) and it is **reproducible**: `random()` would reshuffle the draw on every retry, which would break the promise "this is the soul I am guarding".
- [2026-10-22] [Cycle key]: the fraternity cycle key is `fraternity:<group_id>:<YYYY>-W<ww>` and the challenge key is `challenge:<group_id>:<starts_on>` -> the brief suggested a global `YYYY-Www`, but `UNIQUE (cycle_key, guardian_id)` would then collide for a member who belongs to two fraternities in the same week; the key must identify the group.
- [2026-10-22] [Eligibility]: a member is drawn only when the master switch is ON **and** a per-group `guardian_angel_opt_ins` row exists **and** the membership is active **and** the member is not blocked with any other candidate -> a member who did not opt in is never paired and never learns they were excluded; a blocked pair removes **both** members (the block is symmetric).
- [2026-10-22] [Idempotency]: the pairing is upserted on `(cycle_key, guardian_id)` and never re-shuffles a cycle; when the eligible set changes mid-cycle the existing pairing is kept (the protected slot is already taken) -> re-running the job must never move a soul that is already being prayed for.
- [2026-10-22] [Reveal]: `public.reveal_guardian_identities()` is `service_role` only and the daily `a8_reveal_ended_cycles` job calls it for the cycles whose `cycle_ends_on` is in the past -> "revealing identities only at the end of the cycle" is a product promise, so the reveal is a server action, never a client one.

## 2026-10-22 · Architecture & security

- [2026-10-22] [RPC shape]: every client-facing RPC is a **SECURITY INVOKER** pass-through in `public` that forwards to a `private` implementation (SECURITY DEFINER, `set search_path = ''`), exactly like A3 -> A1's open WARN is about `security definer` functions in the exposed `public` schema; this way A8 adds **ZERO** findings to `authenticated_security_definer_function_executable` (verified: the advisor lists 33 functions, none of them A8's).
- [2026-10-22] [Caller identity]: no A8 RPC accepts a user id — the caller is always `auth.uid()` -> a client could otherwise impersonate another member and read their assignment or send a nudge in their name.
- [2026-10-22] [Outbox writes]: `public.notification_outbox` has no client INSERT/UPDATE/DELETE policy and no client write privilege; the client grant omits `dedupe_key` and `last_error` -> the outbox is written only by `security definer` RPCs and by the `service_role` Edge Function; the dedupe key is an internal idempotency token, not user data.
- [2026-10-22] [Outbox emission]: the notification is queued **in the same transaction** as the write that caused it (triggers) -> no dual write, no lost notification, and a rolled-back transaction never sends a push.
- [2026-10-22] [Dedupe keys]: `prayed:<intention_prayer_id>`, `amen:<amen_reaction_id>`, `nudge:<nudge_id>`, `pinned:<notice_id>:<member_id>` -> one event, one key, `UNIQUE (dedupe_key)` makes the emission idempotent no matter how many code paths reach it.
- [2026-10-22] [Claiming]: `public.claim_notification_outbox()` claims with `FOR UPDATE SKIP LOCKED` -> ad-hoc PostgREST filters have no row lock, so two dispatchers would deliver the same push twice.
- [2026-10-22] [Cron]: the jobs are unscheduled before they are scheduled (migration 0703) and the dispatcher is a **no-op** until `private.app_settings.push_dispatch_url` is set -> `cron.schedule` upserts on (jobname, username, schedule), so an unschedule-then-schedule is the only way to guarantee exactly one row per job name; a project without push configured must never make an outbound call.
- [2026-10-22] [Cron → Edge]: the database authenticates to the Edge Function with a shared secret (`private.app_settings.push_dispatch_secret` → `x-push-secret`), never with the service-role key -> the service-role key never has to be stored in the database.
- [2026-10-22] [Edge Function auth]: `push-dispatch` is deployed with `verify_jwt: false` and verifies the caller itself (service-role bearer **or** `x-push-secret`) -> its caller is `pg_cron` through `pg_net`, which has no user JWT; failing closed with 401 is the only safe behaviour.
- [2026-10-22] [APNs signature]: the JWS carries the **raw** `R || S` signature (RFC 7515 §3.4), not the DER form -> the A8 brief stated the opposite, but a DER signature makes every provider token invalid (`InvalidProviderToken`); the DER conversion is implemented and exported anyway (`rawSignatureToDer` / `derSignatureToRaw`) behind the `JWS_SIGNATURE_ENCODING` switch, so the decision is documented, reversible and testable.
- [2026-10-22] [No fake success]: a transport failure marks the outbox row `failed` with the real error and reschedules it -> APNs requires HTTP/2 and the Edge Runtime may negotiate HTTP/1.1; reporting a fake `200` would silently drop every notification. The production alternative (a dedicated HTTP/2 sender service) is documented in `docs/backend/PUSH.md`.
- [2026-10-22] [A5 seam]: migration 0704 replaced the body of `public.emit_prayer_notification` (same signature, same `service_role`-only privilege, same `{"emitted":bool,"reason":text}` shape) and added `trg_intention_prayers_notify` -> A5's body inserted into columns (`recipient_id`, `actor_id`, `kind`) that do not exist in the A8 outbox; SCHEMA.md §15.6 explicitly allows A8 to replace the body. A5's `toggle_prayed_for` calls the seam **and** the trigger fires — both resolve to `prayed:<intention_prayer_id>`, so exactly ONE push is created (asserted in the A8 suite).

## 2026-10-22 · Cross-agent

- [2026-10-22] [A4]: `streak_milestone` is reserved in the `notification_type` CHECK but no trigger emits it -> A4 owns `streaks` / `streak_events` and the brief forbids A8 from touching them; the type is ready for an A4/A9 follow-up.
- [2026-10-22] [A6]: A6's moderation RPCs may hide a feed post or a chat message, but the outbox row of the reaction that is being hidden is not retracted -> a push that is already in the outbox is delivered; a later A6/A8 iteration may add the retraction.
- [2026-10-22] [A9]: the client surface is the RPC list in SCHEMA.md §19.4; `guardian_angel_pairings` and `notification_outbox` must be read through the RPCs (or with the explicit column list for the outbox) because the table-level `SELECT` is revoked or column-restricted.
