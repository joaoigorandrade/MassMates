# A2 — Auth & account lifecycle decisions

Format: `[YYYY-MM-DD] [Topic]: Decision -> Reason (why alternatives failed)`

- [2026-10-22] [private schema pattern]: every A2 RPC is a thin `SECURITY INVOKER` public wrapper over a `SECURITY DEFINER` implementation in the non-exposed `private` schema -> keeps the `authenticated_security_definer_function_executable` count flat (verified: unchanged) while the enforcement still runs with the owner's privileges; a `SECURITY DEFINER` wrapper in `public` would have added 5 findings.
- [2026-10-22] [private schema ACL]: `revoke execute … from public` is NOT enough — the platform's default ACL grants `anon` a direct EXECUTE grant that survives it -> migration `0105` revokes from `public, anon` explicitly; `authenticated` keeps EXECUTE because the wrappers delegate with the caller's privileges.
- [2026-10-22] [handle_new_user]: the trigger inserts the profile as `SECURITY DEFINER` with `EXECUTE` granted only to `supabase_auth_admin` -> `public.profiles` has FORCEd RLS and no client INSERT policy, so this is the only writer; `anon`/`authenticated` must not be able to call the trigger function directly.
- [2026-10-22] [display_name fallback]: the gendered fallback `Irmão`/`Irmã` is chosen from `raw_user_meta_data.gender` and defaults to `Irmão` -> the profile is created inside the signup transaction, where no request context exists to infer anything else.
- [2026-10-22] [avatar_path at signup]: only an `avatars/…` value from the metadata is stored, external provider URLs are dropped -> `public.profiles.avatar_path` is a STORAGE PATH, not a URL (SCHEMA.md §2.1); accepting a URL would also let a user point at another bucket.
- [2026-10-22] [profile validation]: a BEFORE UPDATE trigger (`trg_profiles_a2_validate`) re-runs the A2 validations -> a direct PostgREST `PATCH /profiles` would otherwise bypass every rule the RPC enforces; revoking the table-level UPDATE privilege would have broken other agents' flows (A8 sets `guardian_angel_opt_in`).
- [2026-10-22] [rule_of_life shape]: an entry accepts EXACTLY the keys `kind` and `label` -> the column is public and free-text is a privacy risk; an unknown key is rejected rather than ignored.
- [2026-10-22] [ad consent]: `update_ad_consent` requires BOTH flags and always writes an `account.ad_consent_updated` row to `public.audit_log` -> the consent surface must be auditable and unambiguous; consent is never derived from metadata or from spiritual-practice data.
- [2026-10-22] [two-tap deletion]: the request row is the server-side proof; `request_account_deletion` is idempotent (a partial unique index allows one live row per user) -> the client may retry the first tap, and the Edge Function refuses to erase anything without a confirmed, unexpired row owned by the caller.
- [2026-10-22] [deletion window]: the whole two-tap flow (request → confirm → Edge Function) must complete within 15 minutes of the request -> the token is short-lived; a stale request is flipped to `expired` by the next request call.
- [2026-10-22] [group ownership on deletion]: a group created by the departing user is DELETED when no member remains, otherwise the ownership is TRANSFERRED (longest-standing admin, else the longest-standing member promoted to admin) -> deleting a group that still has members would destroy other people's community; `groups.created_by` is `ON DELETE SET NULL`, which would silently orphan the group.
- [2026-10-22] [deletion order]: the request row is marked `completed` BEFORE the auth user is deleted -> `account_deletion_requests.user_id` cascades with `public.profiles`, so the row would already be gone; the durable record is the `account.deleted` row in `audit_log` (no FK on `actor_id`).
- [2026-10-22] [Edge Function auth]: the deployed `delete-account` keeps `verify_jwt: true` AND re-verifies the JWT inside the function with `auth.getUser(token)` -> the service role is used only for the destructive deletes, and the user id always comes from the verified claims, never from the request body.
- [2026-10-22] [storage erasure]: an object is deleted only when the caller's uuid is one of its path segments (witness-photos are `group_id/user_id/uuid.jpg`) -> a group's cover belongs to the group, not to the uploader; deleting it would remove an asset other members still use.
- [2026-10-22] [A1 test fixture]: `supabase/tests/a1/foundation.sql` now upserts its profile fixture (`on conflict (id) do update`) -> A2's `on_auth_user_created` trigger creates those profiles first, so the plain INSERT raised a duplicate-key error; the assertion count and the meaning of the fixture are unchanged (81/81 PASS).
- [2026-10-22] [SQL wrapper arity]: the public wrappers are `plpgsql`, not `sql` -> in a `language sql` body the named parameters are not resolved when the body is validated at CREATE time, so `create function` failed with `function private.update_my_profile_impl() does not exist`.
- [2026-10-22] [comment on function]: every `comment on function` names the full argument list -> `comment on function private.update_my_profile_impl ()` does not match the 9-argument function and aborts the whole migration with `42883`.
- [2026-10-22] [error keys]: every validation raises `RAISE EXCEPTION '<key>' USING ERRCODE = '22023'` with the detail in `HINT` -> A9 maps a stable, machine-readable key to the pt-BR / en sentence; the SQLSTATE stays `22023` for every invalid parameter.
