# A5 — decisions

## 2026-10-22 · Schema & privacy

- [2026-10-22] [Tables]: A5 owns `feed_posts`, `amen_reactions`, `prayer_intentions`, `intention_prayers`, `chat_messages`, `pinned_notices` in the `0400` prefix range -> the feed is derived from A4's group-shared check-ins, the Prayer Wall and the chat are group-scoped content; vertical slicing keeps A5's domain in one place.
- [2026-10-22] [Sacred privacy]: `feed_posts` carries a hard CHECK `practice_kind <> 'confession'` -> A4's fan-out already refuses a confession check-in, but the constraint makes the guarantee independent of A4's code (a confession can never reach the feed even if a future writer tries).
- [2026-10-22] [Sacred privacy]: `prayer_intentions` is documented as PUBLIC group content and never receives Spiritual Diary or Confession content -> a prayer intention is a prayer *request*, not a diary entry; the comment on the table states the boundary explicitly.
- [2026-10-22] [Writes]: `feed_posts` has **no** client INSERT/UPDATE/DELETE policy, and `prayer_intentions` / `pinned_notices` only grant `update (body)` column-level -> the server owns the counters (`prayer_count`) and the moderation flags (`is_hidden`); without the column-level grant a member could set `prayer_count = 999` on their own intention.
- [2026-10-22] [Writes]: the "I Prayed for You" counter is kept in sync by the trigger `trg_intention_prayers_count` (AFTER INSERT +1 / AFTER DELETE -1, floored at 0) implemented by `private.a5_sync_intention_prayer_count()` (SECURITY DEFINER) -> a SECURITY DEFINER trigger can write the counter even though clients have no UPDATE privilege on the column.

## 2026-10-22 · Security & architecture

- [2026-10-22] [Implementation schema]: all A5 implementation helpers live in the non-exposed `private` schema (`a5_iso`, `a5_cursor_ts`, `a5_cursor_id`, `a5_cursor_text`, `a5_visible_post_group`, `a5_visible_intention_group`, `a5_sync_intention_prayer_count`) with `EXECUTE` revoked from `public/anon/authenticated/service_role` -> A1 warned against adding `security definer` functions to `public` that leak data; the public schema now only carries the documented RPC surface, and the helpers are not reachable through PostgREST.
- [2026-10-22] [Blocks]: every read path excludes blocked content **in both directions** (`public.is_blocked()` is symmetric) -> a block must hide the blocker's content from the blocked user and vice-versa, otherwise "block" is meaningless.
- [2026-10-22] [Hidden posts]: a hidden post is invisible to plain members but visible to group admins -> the admin still needs to moderate and audit the content.
- [2026-10-22] [A6 seam]: `public.soft_delete_feed_post(p_post_id)` is group-admin-only and writes one `public.audit_log` row -> A6 owns moderation but must not write my table directly; the seam keeps the audit trail inside the same transaction as the hide.

## 2026-10-22 · Pagination & API

- [2026-10-22] [Cursor]: `p_before` is `text` and the cursor is `"<created_at ISO-8601 UTC>|<uuid>"` -> a `timestamptz` parameter cannot carry the composite key, so a strict keyset pagination (no duplicate, no skip on equal `created_at`) would be impossible; a bare timestamp is still accepted but compares strictly and may skip ties.
- [2026-10-22] [Pagination]: keyset pagination lives inside the RPCs (no views) -> the RPC is the only client surface, so the cursor, the visibility rules and the clamping stay in one place and no extra view can drift from them.
- [2026-10-22] [Ordering]: the chat RPC returns **newest first** (same as the feed) -> a single ordering convention for every paginated list; the client reverses the array for the bottom-up chat UI.
- [2026-10-22] [Realtime]: `chat_messages`, `amen_reactions` and `intention_prayers` are in the `supabase_realtime` publication with `REPLICA IDENTITY FULL` -> RLS is enforced by the `postgres_changes` channel for `authenticated` subscribers, so the existing policies already protect the live feed.

## 2026-10-22 · Cross-agent

- [2026-10-22] [A4]: A4's `trg_check_in_destinations_fanout` inserts directly into `public.feed_posts`; A5 additionally exposes the validated, idempotent `public.insert_feed_post(...)` -> the trigger works as-is (the definer bypasses RLS) and the seam is the safe alternative for any future writer.
- [2026-10-22] [A8]: `public.emit_prayer_notification(p_intention_id, p_prayer_id)` is a no-op while `public.notification_outbox` does not exist (guarded with `to_regclass`) -> A8 is Wave 3, so the FK/table could not be created now; the seam lets the notification switch on the moment A8 creates the table plus the documented trigger.
- [2026-10-22] [Migrations]: `0405_fix_feed_rpc_page_scope` re-applies the three paginated RPCs -> `0402`/`0403` were applied to the shared project with a missing `FROM page pg` in the outer select of the page CTE; the migration files were corrected in place and `0405` brings the live database in line.

## 2026-10-22 · Chat moderation (A6 gap report)

- [2026-10-22] [Chat moderation]: `public.chat_messages` gained `is_hidden`, `hidden_reason` and `hidden_at` (migration `0407`) -> A6 reported that `hide_content('chat_message', …)` could record the trail but not actually hide the message; chat moderation is in scope (group admins must remove inappropriate content, App Store UGC needs a working report -> hide path).
- [2026-10-22] [Chat moderation]: the `chat_messages` SELECT policy now mirrors `feed_posts` exactly — `(not is_hidden or is_group_admin(group_id, auth.uid()))` -> a hidden message is invisible to ordinary members but stays visible to the group admins, who still need to moderate and audit it.
- [2026-10-22] [Chat moderation]: `public.soft_delete_chat_message(p_message_id)` mirrors `public.soft_delete_feed_post` (same privilege pattern, same `audit_log` shape, same jsonb shape) -> A6 can delegate any chat moderation the same way it delegates a post moderation, and the two paths stay symmetric.
- [2026-10-22] [Privileges]: `revoke execute on function public.soft_delete_chat_message (uuid) from public, anon` -> this project's default ACL grants EXECUTE on new `public` functions to `anon` explicitly, so revoking "from public" alone leaves `anon` able to call the function (A6 found this); verified with `has_function_privilege('anon', …, 'execute') = false`.
- [2026-10-22] [hidden_at]: `hidden_at` has no default and is never set automatically on UPDATE -> only the moderation RPC stamps it, so "hidden at" always means "hidden by a moderator", not "last touched".
- [2026-10-22] [RPC visibility]: `public.get_chat_messages` gained the `is_hidden` filter and `public.create_chat_message` refuses a reply to a hidden message -> both RPCs are SECURITY DEFINER and therefore bypass RLS, so they must apply the visibility rules themselves (same reason `get_feed_posts` filters hidden posts).
- [2026-10-22] [A6 cross-check]: A6's `private.auto_hide_content()` already contained a column-guarded `update public.chat_messages set is_hidden = true`, so A6's `hide_content` needed NO change -> the guard `private.has_column (v_tbl, 'is_hidden')` started passing with migration 0407; proven end-to-end in `supabase/tests/a5/chat_moderation.sql` (A6's path sets only `is_hidden`; `hidden_reason` / `hidden_at` remain NULL, which is A5's RPC's job).
- [2026-10-22] [A8 seam]: A8 replaced the body of `public.emit_prayer_notification` and created `trg_intention_prayers_notify` (migration 0704) -> my `toggle_prayed_for` still calls the function, so the RPC path and the trigger both fire; the outbox `dedupe_key` (`prayed:<intention_prayer_id>`) + `ON CONFLICT DO NOTHING` makes them idempotent, so the author of an intention gets exactly ONE push (asserted in the A5 suite).
