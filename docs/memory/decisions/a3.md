# A3 · decisions — groups, invites, slots

[2026-10-22] [Slot model]: `fraternity` = personal slot (max 2, +1 for 30 days after a rewarded video), `challenge` = seasonal slot (max 1) -> the plan says "2 Personal Groups + 1 Featured Seasonal Challenge"; the spec assigns the seasonal slot to every challenge, so a user can never hold two seasons at once. `personal_used`/`seasonal_used` count only ACTIVE memberships (group not archived, and a challenge whose `ends_on` has not passed).

[2026-10-22] [Invite code generation]: 6 digits from `lpad(floor(random()*1000000)::bigint::text, 6, '0')`, 20 bounded attempts, under a transaction-scoped advisory lock (`pg_advisory_xact_lock(hashtext('massmates.group_invite_code'))`) -> a check-then-insert without the lock can hand the same code to two concurrent creators; an unbounded loop could spin forever.

[2026-10-22] [Invite code scope]: a code is free only when it is not the `invite_code` of ANY group (archived included) and not the code of a live `group_invites` row -> retired codes must stay unusable, otherwise a shared link could silently re-open a group.

[2026-10-22] [RPC shape]: the exposed `public.*` RPCs are `SECURITY INVOKER` pass-throughs, the privileged work lives in `private.*_impl` (`SECURITY DEFINER`, `set search_path = ''`) -> A1's §3.2 remediation: a `SECURITY DEFINER` function in the exposed `public` schema that `authenticated` may call is a `authenticated_security_definer_function_executable` advisor finding; this way A3 adds ZERO new findings.

[2026-10-22] [anon preview]: no `anon` SELECT policy on `public.groups`, the preview goes through `public.preview_group_by_code()` / `public.list_featured_challenges()` -> RLS is row level, so an `anon` policy would also expose the `invite_code` and `created_by` columns of every visible row. The exact column-level grant recipe is written down in SCHEMA.md §14.7 for A10.

[2026-10-22] [anon implementation schema]: the two public preview implementations live in a dedicated schema `a3_preview`, and `anon` has NO `USAGE` on the shared `private` schema -> `private` is shared with A2/A4/A5/A6 and several of their functions keep the default ACL (EXECUTE to PUBLIC); granting `anon` USAGE there would have exposed `private.recompute_streak()` and `private.on_check_in_deleted()` to unauthenticated clients.

[2026-10-22] [Double grant]: the "one active group_slot per user" rule is enforced inside `public.grant_slot_unlock()` (returns the existing row instead of inserting), the index on `(user_id, kind)` is NOT unique -> a partial unique index with `now()` in the predicate is impossible because `now()` is not immutable. The second call is a no-op, it never extends the 30 days, so a rewarded video cannot be replayed to extend the bonus forever.

[2026-10-22] [Admin rules]: one admin per group; the last admin cannot leave or be removed; an admin may remove another admin as long as one admin remains; `transfer_admin` demotes every other admin; the last member leaving archives the group -> keeps "who is in charge" unambiguous and matches the "manage members, reset invite codes" admin menu of the plan (Flow 4).

[2026-10-22] [A1 bug found by A3]: `public.set_updated_at()` now only writes `updated_at` when the relation has that column (migration 0209) -> A1 attached `trg_group_members_updated_at` to `public.group_members`, which has no `updated_at` column, so EVERY update on that table failed with `42703` (it broke A1's own `group_members_update_admin` policy and A3's `transfer_admin`). Reported to the orchestrator; A1 owns the function.

[2026-10-22] [A7 dependency]: `public.group_featured` is created in A3's FIRST migration (0201) so A7 can FK `public.sponsored_challenges` to it -> the FK constraint `sponsored_challenges_featured_group_id_fkey` is in place; A7 may publish through `public.set_featured_group()` (service_role only) instead of writing the table directly.
