# A4 · Check-In Engine, Streaks & Scoring

- [2026-10-22] [Privacy gate]: `check_ins` carries two table-level CHECKs (`check_ins_private_has_no_content_ck`, `check_ins_confession_is_private_ck`) plus NO client INSERT/UPDATE policy -> Reason: a client could otherwise forge a private/confession check-in carrying content; the table must be physically unable to hold it (CONVENTIONS §8).
- [2026-10-22] [Private fan-out]: a private check-in creates ZERO `check_in_destinations` rows -> Reason: the destination table IS the privacy boundary; group visibility comes from the feed, never from `check_ins`.
- [2026-10-22] [Streak vs Ring]: the Daily Streak and the Rule of Life Ring are two independent computations (streak = >= 1 practice/day, public OR private; ring = % of `profiles.rule_of_life` commitments done) -> Reason: the product plan (Part 2 §2) requires them to be decoupled so a private practice never pressures the user and a partial day never breaks the streak flame.
- [2026-10-22] [Streak algorithm]: the streak is recomputed from the AUTHORITATIVE active-day set (`check_ins.local_date` UNION `streak_mercy_uses.repairs_date`) in `private.recompute_streak()`, instead of being incremented incrementally -> Reason: incremental counters corrupt on out-of-order back-fills and cannot express a repaired day; the set computation is idempotent and handles mercy for free.
- [2026-10-22] [Streak decay]: the streak does NOT decay on its own; it resets to 1 on the next check-in after a gap (audited as a `reset` event) -> Reason: an auto-decay would make the streak unreadable (it would be 0 for anyone who did not practise today) and would make Streak Mercy useless.
- [2026-10-22] [Streak Mercy contract]: A7 INSERTS into `public.streak_mercy_grants`; the user consumes it with `public.use_streak_mercy(p_repairs_date)`; the INSERT policy is `service_role` only -> Reason: a grant table owned by A4 with a write path owned by A7 avoids a circular dependency, and a user must never be able to grant mercy to themselves.
- [2026-10-22] [Mercy adjacency]: the repaired day must be adjacent to the current streak (the day before its first day, or the day after its last day) -> Reason: any other day would leave the current streak unchanged, so the mechanic would be a no-op that still burns the monthly allowance.
- [2026-10-22] [Scoring]: `check_ins.points` stores the MAX across the destination groups and `get_group_progress()` recomputes the per-group contribution -> Reason: one check-in can fan out to several groups with different scoring modes; a single stored number would silently under-count the richer group.
- [2026-10-22] [Fan-out trigger]: A4 creates the trigger on its OWN table `check_in_destinations` and A5 creates none -> Reason: removes the ordering dependency between A4 and A5; the trigger function no-ops while `public.feed_posts` does not exist.
- [2026-10-22] [Implementation schema]: the streak engine lives in the non-exposed `private` schema with `search_path = ''` and fully-qualified names, the public RPCs are narrow wrappers -> Reason: A1's warning — a `security definer` function in `public` that reads tables the caller cannot see must not expose that data.
- [2026-10-22] [One check-in per practice per day]: `UNIQUE (user_id, practice_kind, local_date)` on `check_ins` -> Reason: a single check-in may be shared with several groups, so the uniqueness key is the (user, practice, day) triple, not the destination.
- [2026-10-22] [practice_points]: A4 owns the DATA and exposes `public.set_practice_points()` (group admin only, global rows only for an admin of some group) -> Reason: A1 owns the table and its baseline policies; A1's INSERT policy still lets ANY authenticated user write a GLOBAL row — reported to A1/A10 instead of silently altering another agent's policies.
